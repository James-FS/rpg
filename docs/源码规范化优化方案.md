# 自研源码规范化优化方案

> 目标：让项目更容易定位错误，并避免核心系统在配置错误、存档错误或部分失败后继续以不一致状态运行。
>
> 原则：业务条件不满足时返回清晰的业务失败；程序不变量、必需依赖或内容配置错误应尽早暴露；外部 I/O 错误只在边界捕获并明确反馈。

## 1. 审查范围与总体判断

本方案基于对 `rpg/Assets/Scripts/` 核心自研运行时代码、项目设计文档和包配置的静态检查。没有修改源码，也没有启动 Unity 或运行测试。源码已有较清晰的基础分层：`GameSession` 编排跨系统用例，任务、背包、装备、奖励和好感系统维护各自状态，UI 通过事件刷新。建议在此基础上渐进优化，不做整套架构重写。

当前优先问题集中在：

1. 必需依赖缺失时只记录日志，系统仍继续启动。
2. 未知 ID 或无效状态会被默认值掩盖。
3. 存档读取把“无存档”和“损坏且无法恢复”混为一谈。
4. 多个游戏操作忽略 `Save()` 失败结果，仍返回成功。
5. 奖励提交顺序存在部分成功的可能，注释与实际副作用不完全一致。
6. 部分运行时自动补组件、全局查找和 UI 构建回退掩盖了场景配置问题。
7. AIBot 包引用本机绝对路径，影响工程可移植性。

## 2. 错误处理约定

| 情形 | 处理方式 | 示例 |
|---|---|---|
| 正常业务拒绝 | 返回明确的领域结果，不抛异常 | 任务未接受、玩家物品不足、模型请求不存在的任务 |
| 程序不变量被破坏 | 尽早抛出异常并带上下文 | 缺少必需系统、未知内部任务 ID、必需资产引用为空 |
| 外部文件或服务失败 | 在边界捕获预期异常，返回明确状态并记录完整原因 | 存档读写失败、AIBot Server 不可用 |
| 有意提供恢复能力 | 保留恢复逻辑，并报告恢复结果 | 从 `.bak` 恢复存档、Lua 热重载失败后保留旧模块、GM 测试槽回滚 |

不要为了“避免任何异常”给每个方法增加空值回退。必需依赖由启动组装阶段保证；业务入口只处理其契约允许出现的输入。

## 3. 优先级与整改步骤

### 阶段一：让必需依赖在启动时失败

**现状**

`GameSession`、`SaveSystem`、`QuestSystem`、`EquipmentSystem` 等在 `Awake()` 中发现缺少系统组件时只写 `Debug.LogError`，随后仍可能继续运行。`QuestToolHost.RegisterTools()` 缺少服务时写警告后仍注册工具。`NpcInteractable` 缺少 `NpcAgent` 或 `UIManager` 时延迟到交互时才警告并返回。

**方案**

- 在 AppRoot 的组装/初始化入口统一检查必需系统，缺项时抛出带组件名的 `InvalidOperationException`，并阻止进入可玩场景。
- 让 `QuestToolHost` 在依赖未绑定时初始化失败，不注册一组只能部分工作的工具。
- 将 NPC 必需的 `NpcAgent`、正式 UI 入口及场景门配置作为 Prefab/场景契约，在启动或编辑器校验阶段报告。
- 避免多个组件分别执行“检查、打印、继续”的重复逻辑。

### 阶段二：区分“必需查询”和“可能不存在的外部输入”

**现状**

`QuestSystem.GetState()` 对未知 questId 返回 `Available`。这会把任务 ID 拼错、配置遗漏或存档问题伪装成正常的未接取状态。`ItemDatabase.GetById()` 对缺失物品打印警告并返回 `null`，内部配置引用问题可能直到运行流程中才暴露。

**方案**

- 对系统内部的必需查询使用 `GetRequiredQuest`、`GetRequiredItem` 一类接口；ID 不存在时抛出异常并附上调用上下文。
- 对来自玩家输入、模型工具调用或可选查询的 ID 使用 `TryGet...`，由调用边界返回明确的业务失败。
- 移除未知任务自动映射到 `Available` 的默认行为。
- 在加载内容数据时校验任务和物品 ID 唯一性，并验证任务目标物品、奖励物品、接受任务物资、NPC 好感配置等必需引用。
- 对 `InventorySystem.Add`、`GameSession.PickupItem` 等公共写入口定义数量契约。配置或内部调用传入非正数量应暴露为程序错误；来自外部工具的非法参数应返回工具失败。

### 阶段三：明确存档读取和写入结果

**现状**

`SaveSystem.Load()` 在没有存档时返回 `null`，在主档与备份都不可用时也返回 `null`。`LoadAndApply()` 因此无法区分新游戏与数据损坏；启动流程可能继续使用默认状态。另一方面，`Save()` 捕获所有 `Exception` 并返回 `false`，调用 `Save()` 的多个 `GameSession` 用例没有检查返回值，仍然报告业务成功。

**方案**

- 把读取结果明确区分为 `NoSave`、`Loaded`、`RecoveredFromBackup`、`Corrupt` 等状态。
- `NoSave` 正常进入新游戏；`RecoveredFromBackup` 明确提示并保留恢复日志；`Corrupt` 阻止静默开新局或覆盖用户进度。
- 将 `Save()` 的捕获范围收窄到文件系统边界的预期异常。状态快照组装、数据约束等程序错误应保留异常和堆栈。
- 所有 `GameSession` 用例必须处理保存结果。保存失败时返回明确结果，不得让对话工具宣称“已完成并保存”。
- 统一保存失败后的内存状态语义：选择回滚，或明确标注“本次运行已生效、磁盘未保存”，并为可重试用例保证幂等。
- 保留临时文件、JSON 校验和 `.bak` 恢复机制；这些属于明确的数据恢复能力。

### 阶段四：整理任务领奖提交顺序

**现状**

`GameSession.CompleteQuest()` 先由 `RewardService.GrantQuestReward()` 扣除任务物品并增加奖励，再调用 `QuestSystem.ClaimReward()` 推进任务状态。若后一步失败，奖励副作用已经发生；对应失败分支的注释却写成“不会产生额外副作用”。事件在金币和背包变化时会同步触发，也要考虑观察者是否能看到中间状态。

**方案**

- 将领奖定义成单一提交过程：先校验任务状态、物品数量和奖励配置，再按固定顺序更新任务、背包、金币与好感。
- 在提交完成前不广播外部可观察的变更事件；提交完成后统一发布事件。
- 对“任务状态已是 Rewarded”“目标物品不足”等正常业务条件返回领域失败。
- 对预检通过后仍违反内部不变量的情况抛出异常；不要用普通 `false` 把部分提交伪装成正常拒绝。
- 修正注释，使其与真实的失败语义一致。

**涉及代码**

### 阶段五：集中依赖绑定，移除隐式运行时修复

**现状**

`FindObjectOfType` 分散在 `GameSession`、`SaveSystem`、NPC 工具、物品拾取和场景门等代码中。`EnemyWolf.Awake()` 在缺少 `CharacterController` 时自动添加组件。启动对象还通过 `GameObject.Find("AppRoot")` 的名称判断是否完成初始化。

**方案**

- 由 AppRoot/场景加载入口负责注入系统引用和当前 Player 引用，业务脚本不在运行时全局搜索服务。
- 通过明确的 AppRoot 组件或单例状态识别已初始化系统，不用 GameObject 名称代表初始化完成。
- 对必需组件使用组件约束，并让 Prefab 配置缺失直接暴露；移除自动补组件行为。
- 保留场景切换时更新 Player 引用的显式生命周期入口。

**涉及代码**

### 阶段六：规范外部包和工具配置

**现状**

[`Packages/manifest.json`](../rpg/Packages/manifest.json) 通过本机绝对路径引用 AIBot 包。NPC 工具 ID 同时配置在游戏侧 Profile 和 AIBot Server 配置中，两端不一致时 Server 可能过滤工具。

**方案**

- 把 AIBot 包迁移为仓库内可移植的本地包、稳定的包版本或相对引用。
- 记录并版本化当前对 AIBot SDK 的必要补丁，升级时让补丁可复现。
- 对客户端和 Server 的工具白名单增加启动期一致性校验，或者从一个权威配置生成两侧配置。

### 阶段七：较低优先级的职责与 UI 整理

- `PlayerController` 同时负责原始输入、移动、跳跃、蹲伏、攻击、受伤、死亡和复活入口。后续新增玩法前，可拆分移动与战斗职责，保留 `PlayerController` 作为协调接口。
- `QuestPanel` 与 `InventoryPanel` 的构建和刷新代码较长；明确一条正式 UI 构建路径。生产 Prefab 缺少必需引用时让校验失败，避免“警告后使用不完整界面”。
- `QuestPanel.RebuildList()` 每次刷新都会销毁并重建所有任务行。任务数量增长后改成缓存行并只更新变化项；当前规模下优先级较低。
- 考虑将 `QuestResult` 中的业务结果与中文展示文本分开，避免领域流程同时承担本地化和 AI 回复文案。

## 4. 有意保留的异常捕获

以下异常处理对应明确的恢复行为，不建议为追求“所有异常都抛出”而直接删除：

- `SaveSystem` 读取主存档失败后尝试 `.bak`。
- Lua 热重载失败后保留旧模块，待脚本修复后重新加载。
- GM 测试槽异常时恢复进入测试前的游戏状态和 NPC Profile。
- 标题界面归档旧旅程失败时阻止启动新旅程，并给用户明确提示。

需要改进的是错误是否被清楚区分和反馈，而不是取消有价值的恢复流程。

## 5. 验收标准

实施完成后应满足：

1. 缺少必需系统或场景配置时，在启动阶段出现异常和明确组件/资产信息，不进入半可用游戏状态。
2. 未知内部 questId 不会被映射为 `Available`；外部无效工具参数返回明确的工具失败。
3. 没有存档、从备份恢复、所有存档损坏三种路径可区分；损坏状态不会静默按新游戏覆盖。
4. 每个跨系统用例都检查保存结果，任何“成功”响应都符合约定的持久化语义。
5. 领奖失败不会留下“物品已扣、金币已发、任务未领奖”的部分状态。
6. 必需资源引用错误在启动/内容校验时暴露，而不是在玩家执行任务中途才出现。
7. 工程不再依赖开发机上的绝对包路径，AIBot 工具白名单配置可以验证一致性。

## 6. 实施建议

按阶段一至阶段四的顺序先处理启动契约、错误分类、存档和领奖一致性；之后集中整理依赖绑定与外部包配置；最后再拆分大类和优化 UI。每个阶段单独提交并做对应验证，避免一次性大改导致难以定位回归问题。

## 7. 本轮执行记录（2026-10-31）

### 已落实

- AppRoot 的任务、背包、装备、奖励、好感、存档、流程和 UI 系统在依赖缺失时抛出异常；玩家、狼、场景门和 NPC 的必需配置改为启动或初始化时报错。
- 物品、任务、NPC 配置在加载时校验 ID、重复项、引用和关键数量；未知内部 `questId` 不再默认为 `Available`。NPC 工具注册会检查本地 Profile 是否启用了四个必需工具。
- 存档读取返回 `NoSave`、`Loaded`、`RecoveredFromBackup`、`Corrupt` 结果；保留 version 1 存档迁移和备份恢复。无法恢复时回到标题界面显示错误。
- `GameSession` 的任务、拾取、装备、消耗品、丢弃和好感操作统一使用快照事务；写盘失败会恢复操作前状态并向调用方返回失败。内部异常回滚后重新抛出。
- 存档写入仅在文件 I/O 边界处理预期磁盘异常；快照和内容约束错误直接抛出。场景、UI、NPC 工具、掉落物和背包物品入口统一从 `GameSession` 获取系统引用，当前玩家仅由场景边界绑定。
- AIBot 包地址从开发机绝对路径改为相对的同级仓库路径：`../../../aibot/Packages/com.aibot.npcagent`（相对 `rpg/Packages/` 目录解析）。项目仍要求 `aibot` 仓库与 `rpg` 仓库保持当前相对目录结构；本轮没有复制或改动外部 AIBot 仓库。

### 尚未处理

- `PlayerController` 的移动/战斗职责拆分、任务列表的行复用，以及 UI 预制体与代码构建回退路径的合并属于低优先级结构整理，本轮未做大范围重构。
- 客户端工具白名单已做启动检查；AIBot Server 端白名单仍维护在外部仓库，本轮没有改动该仓库或其现有工作区内容。

本轮只做了源码静态检查和 `git diff --check`，没有启动 Unity、编译项目或运行自动化测试。
